## Exact missing privileges

The following statements describe the minimum additional columns used by the
current handlers. `VERIFIED_PUBLIC_API_ROLE` is an intentionally non-executable
placeholder for the role proven by the protected binding observation. It must
be quoted as an SQL identifier, never interpolated from untrusted input.

```sql
GRANT SELECT (id, user_id, reward_id, reward_level, reward_title, redeemed_at, status)
  ON trust.reward_redemptions TO VERIFIED_PUBLIC_API_ROLE;
GRANT INSERT (id, user_id, reward_id, reward_level, reward_title)
  ON trust.reward_redemptions TO VERIFIED_PUBLIC_API_ROLE;
GRANT USAGE ON SCHEMA editorial TO VERIFIED_PUBLIC_API_ROLE;
GRANT SELECT (id, title, post_id, published_at)
  ON editorial.publications TO VERIFIED_PUBLIC_API_ROLE;
```

No new function or sequence privilege is needed. Rewards IDs are generated by
the application; `redeemed_at` and `status` use existing database defaults. The
canonical role already has `USAGE` on `trust` and existing access to the joined
identity, content, social, rate-limit, idempotency and activity relations. The
live preflight must verify those prerequisites rather than expand them silently.
There is no request for UPDATE/DELETE on either table, schema CREATE, role
membership, BYPASSRLS, admin access, entitlement writes, credentials or billing.

## Consequences and acceptance

Column privileges do not provide row isolation. The repository tables have no
RLS policy in the approved migration source; synthetic PG17 confirms RLS is
disabled. If production matches, a holder of the runtime database identity could
read all rows in those granted columns and insert reward records for any valid
user, subject to database constraints. JWT ownership, account maturity,
reputation eligibility and Black access are enforced in the application. This
is a material permission expansion even though route checks remain unchanged.
Publication column grants also permit direct reads of unpublished rows; the
route filters them. Do not describe the SQL grants as database-enforced
per-user or published-only access. Live RLS/policy differences require review;
do not disable RLS or grant BYPASSRLS to make a test pass.

The reward API maps stored `confirmed` to wire `redeemed`, preserves `revoked`,
includes authenticated `userId`, and uses the persisted redemption timestamp.
A revoked record remains in history and continues consuming the unique
`(user_id, reward_id)` slot; it is not a new authorization to redeem. Paid
membership never grants reputation or reward eligibility. This does not change
the disabled monthly v2 policy, its approved 13,650 maximum or quarterly rules.

The required `--membership-rewards` test group creates fresh owned loopback
PostgreSQL 17 databases. It first demonstrates canonical rewards failure and
Black News Board failure, then introduces the exact column grants **only into
those disposable databases** to exercise route behavior. It covers history
serialization/revocation, persisted timestamps, exact replay, account isolation,
tier neutrality, maturity/reputation rejection, Free/Premium News Board denial,
manual tier grant/downgrade and disabled payment rejection. It is code and
fixture evidence, not a hosted privilege observation or live acceptance.

After approval and independently reviewed execution, refresh effective
privileges through the same binding, validate exact deployed-candidate
authenticated reads with authorized existing accounts, and separately approve
any live redemption/account mutation. Keep publishing and billing gates closed.
Record only sanitized evidence; no account history or private titles in public
Actions artifacts.

Rollback must restore the captured pre-change ACLs for this exact role and
these columns. Do not blindly REVOKE inherited or pre-existing permissions. The
package grants no deletion authority and creates no billable provider resource;
additional request/query usage still remains within existing cost gates.

## Paid billing remains unavailable

Current code has no connected payment provider, checkout, webhook, purchase
ledger, provider customer mapping or entitlement period/cancellation fields.
`identity.user_entitlements` stores manual tiers only. Client purchase/restore
returns `PROVIDER_NOT_CONFIGURED`; `/api/payments*` remains `feature_disabled`.
Worker fixtures prove redirects, forged webhook/client claims and restore
requests cannot grant a tier. Manual Premium/Black is not payment evidence.

A paid integration requires a selected provider and supported web/mobile
purchase route; approved products, prices, currencies, renewal/cancellation,
refund/chargeback, tax and legal terms; existing-account/provider access and
scoped secrets/webhook verification setup; a reviewed customer/event/payment
ledger and versioned entitlement lifecycle schema; signed event authentication,
deduplication and out-of-order reconciliation; account-bound server fulfillment,
expiry/downgrade and purchase restoration; retention/export/deletion policy;
sandbox and exact-candidate acceptance; and explicit activation/cost approval.
No commercial choices, provider access or live charges are inferred here.
Schema proposals and provider adapters can be implemented once these inputs are
specified, while the current disabled boundary remains enforced by CI.
