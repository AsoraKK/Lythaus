# Anti-Scraping Protection Assessment

**Reviewed:** 2026-10-06

**Repository baseline:** `main` at `6cb3bda4ac6a4bfc32381b05c81641b29b7c5e41`

**Scope:** committed application and infrastructure configuration, the existing dated Cloudflare inventory, and current official Cloudflare documentation. This is a source review, not a penetration test or a claim that public data cannot be copied.

## Assessment

Lythaus intentionally serves public marketing pages, profiles, posts, comments, and discovery results. The API has meaningful server-side visibility checks, bounded cursor pages, request limits, and private-response cache headers. Those controls reduce accidental disclosure and per-request abuse; they do not prevent a determined client from collecting content that is intentionally public over repeated requests.

The approved homepage sentence is a policy statement. It does not describe or prove a technical control. No new scraping controls or live security settings were changed for this assessment.

## Existing controls in the repository

| Area | Verified from source | Limits and confidence |
| --- | --- | --- |
| Public content | Anonymous reads are supported for discovery, individual posts, comments, and public profiles. Feed and comment eligibility filters exclude deleted, moderated, unpublished/non-public, and disallowed authorship content. Public profiles return selected fields such as display name, handle, bio, and reputation; the public query does not return account email. See [`index.ts`](../../apps/lythaus-public-api/src/index.ts) and [`feed-runtime-policy.ts`](../../apps/lythaus-public-api/src/feed-runtime-policy.ts). | Public posts and profiles remain fetchable by design, and user-authored public text can itself contain personal information. A public identifier or cursor is not an authorization boundary. |
| Member data | Personal feeds, `/api/users/me`, private feeds, relationships, notifications, activity, and privacy requests/exports pass through a verified active bearer principal. Private API responses use `Cache-Control: private, no-store`. See [`index.ts`](../../apps/lythaus-public-api/src/index.ts). | This is code evidence. Live Worker versions and runtime secrets were not queried. Followers-only content is available only when the authenticated viewer meets the relationship check. |
| Admin data | The admin Worker verifies the Cloudflare Access JWT signature, issuer/audience configuration, and active database membership before dispatching admin routes. It applies an actor-scoped 120-per-minute database rate limit. The waitlist/admin pages use bounded keyset pagination and private cache headers. See [`admin-access-runtime-policy.ts`](../../apps/lythaus-admin-api/src/admin-access-runtime-policy.ts), [`index.ts`](../../apps/lythaus-admin-api/src/index.ts), and [`waitlist-runtime-policy.ts`](../../apps/lythaus-admin-api/src/waitlist-runtime-policy.ts). | The repository's August inventory records an Access-protected admin site, but the current Access application and policy were not independently verified. |
| Pagination and enumeration | Public API pages default to 25 items and cap at 50; handlers fetch one extra row to form a continuation cursor. Some private endpoints deliberately allow up to 100 per page. Discovery tag search is bounded and limited to 30 requests per minute. See [`keyset-cursor.ts`](../../packages/contracts/src/keyset-cursor.ts) and the public API worker. | Pagination limits one response, not the number of pages a client may request. Review every new list/search/export route for a cap, stable cursor, authorization, query cost, and response fields. |
| Application rate limits | The public API applies a default 120-per-minute scoped limit, with 10 per minute for selected auth paths; tag search has a 30-per-minute scope. Authenticated daily action limits also exist. Counters are hashed and written to the existing database rate-limit table. See [`auth-runtime-policy.ts`](../../apps/lythaus-public-api/src/auth-runtime-policy.ts) and the public API worker. | This is app-layer throttling, not crawler identification. Client IP rotation and distributed requests weaken IP-based limits. Each counted request also uses existing Worker/database capacity. |
| Waitlist intake | The handler bounds the JSON body, accepts a fixed field set, verifies Turnstile action and hostname server-side, and requires encryption/HMAC/Turnstile secrets. See [`waitlist-runtime-policy.ts`](../../apps/lythaus-public-api/src/waitlist-runtime-policy.ts). | This only covers waitlist submission. Code and Wrangler configuration do not prove that the live site key, secret, or production deployment is active. It is not a site-wide anti-scraping control. |
| Cache separation | Anonymous discovery is deliberately edge-cacheable for 30 seconds; public posts/comments and public profiles use short public cache lifetimes. Viewer-specific feeds and member data use `private, no-store`. Auth pages have no-store rules in [`_headers`](../../apps/marketing-site/public/_headers). | The marketing homepage has no explicit cache rule in this file. The current Cloudflare Cache Rules and whether any rule overrides origin headers are unknown. |
| Crawler directives | [`robots.txt`](../../apps/marketing-site/public/robots.txt) currently allows every user agent and publishes the sitemap. | Robots directives are requests to crawlers, not authorization or access control; the RFC says they are not a substitute for content security. They must never be used to protect member data. |
| Detection and response | The observability package emits JSON console events with timestamps and correlation IDs. The Alpha response guide sets a P0 privacy/credential incident target of immediate response and requires sanitized incident notes. See [`observability`](../../packages/observability/src/index.ts) and [`support-and-incident-response.md`](../alpha/support-and-incident-response.md). | No source proves request-level crawler analytics, alert delivery, log retention, or a scraping-specific incident playbook is active in production. Audit rows for privileged actions do not detect public crawling. |

The Pages `_headers` file also declares standard browser security headers and a Content Security Policy. These are useful browser protections but do not prevent server-side crawlers from fetching public responses.

## No-additional-spend options

These are capability recommendations based on current official docs, not a claim that they are enabled on the Lythaus zone. Apply only what is already included in the verified current plan. No paid upgrade, new vendor, new resource, or paid crawl program is recommended.

1. **Use AI Crawl Control if present in the current plan.** Cloudflare documents it as available on all plans with per-crawler allow/block and monitoring. On the Free plan, detection relies on user-agent strings and the metrics window is 24 hours; blocking a crawler creates or updates a WAF custom rule. User-agent detection can be evaded, so this is a useful friction layer rather than a guarantee. See [AI Crawl Control overview](https://developers.cloudflare.com/ai-crawl-control/), [getting started and plan limits](https://developers.cloudflare.com/ai-crawl-control/get-started/), and [managing AI crawlers](https://developers.cloudflare.com/ai-crawl-control/features/manage-ai-crawlers/).

2. **Separate behaviors instead of blocking all bots.** Cloudflare exposes Search, Agent, and Training policies to all customers. Given the current no-advertising direction, an “ads pages only” policy is not useful. If approved after observing traffic, a reasonable starting policy is to block Training and Agent crawlers on all pages, preserve ordinary Search, SEO/accessibility checks, feed fetchers, previews, and monitoring bots, and allow an AI Search/partner crawler only by explicit opt-in or agreement. Confirm the September 15, 2026 policy defaults for this existing zone rather than assuming them. See [Cloudflare AI bot policies](https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/) and [verified bot categories](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/).

3. **Keep WAF exploit rules distinct from scraping policy.** Cloudflare documents a Free Managed Ruleset on all plans; for Free zones it protects against a subset of high-impact web exploits and is deployed by default. That is not a crawler block. Custom WAF rules can use actions such as Block or Managed Challenge, but the current zone's rules and eligible features are unknown. See [WAF setup](https://developers.cloudflare.com/waf/get-started/), [managed rules and plan availability](https://developers.cloudflare.com/waf/managed-rules/), and [custom rules](https://developers.cloudflare.com/waf/custom-rules/).

4. **Use a targeted rate limit only if the current plan includes it.** The current Free-plan documentation lists one rule, a 10-second counting/mitigation period, IP counting, and `Path`/`Verified Bot` matching fields. That can add friction to a particularly expensive public search route, but it is not a dataset lock and can be bypassed with distributed IPs. Prefer the existing app limits where they fit; any new application-side counter uses Worker/database capacity. See [Cloudflare rate limiting availability](https://developers.cloudflare.com/waf/rate-limiting-rules/).

5. **Treat Bot Fight Mode as a compatibility tradeoff.** Cloudflare describes the free mode as domain-wide and not customizable or bypassable with WAF rules; it may challenge API and mobile-app traffic. It is not the first choice for a zone serving web, native API, search, and accessibility integrations. See [Bot Fight Mode limits](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/).

6. **Keep shared-cache boundaries explicit.** Retain public caching only for deliberately public responses. Verify Cloudflare cache rules do not cache authenticated/API data or override `private, no-store`; Cloudflare documents those directives as non-storable by shared caches under origin cache control. See [Origin Cache Control](https://developers.cloudflare.com/cache/concepts/cache-control/).

7. **Use existing dashboards and response process before adding telemetry.** If available in the current plan, review AI Crawl Control and Security Analytics/Events for crawler volume, targeted paths, mitigations, and false positives. Keep incident records to UTC time, sanitized correlation/Ray IDs, affected paths, release, severity, and action. Do not log raw request bodies or user content for this purpose. The AI Crawl Control Free analytics window is limited to 24 hours. See [AI Crawl Control plan limits](https://developers.cloudflare.com/ai-crawl-control/get-started/) and the [WAF dashboard overview](https://developers.cloudflare.com/waf/get-started/).

8. **Keep robots guidance accurate, but treat it as voluntary.** After deciding which respectful crawlers should be allowed, a future `robots.txt` update can express those preferences while retaining the sitemap. It will not protect private routes or stop non-compliant clients. See [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html).

2. Review public API enumeration and response/cache rules against expected search, assistive, mobile, feed, and partner clients. Keep private/member data behind the existing server-side authorization checks.
3. If current-plan AI controls are available, review crawler observations and agree on per-category/per-crawler allow/block choices before applying any live change. Avoid blanket rules that interfere with search or user-driven access.
4. Use existing dashboards and the current incident process; add no separately billed log service or provider resource under the no-additional-spend constraint.

Any live Cloudflare setting, privacy default, credential, plan, code-level security control, or new resource remains out of scope for this slice and needs its own precise approval. All new Worker/database enforcement should first be checked for incremental usage against the budget. No anti-scraping mechanism makes intentionally public content impossible to collect, and no such claim is made here.
