# Tag search rollout gate

The `GET /api/feed/discover?tag=...` contract is defined, but the tagged request
currently returns `503 tag_search_unavailable`. The deployed schema has no
maintained exact hashtag index. `feed.topic_memberships` exists, but this
checkout has no runtime writer or reader for it and its `topic` value has no
contract tying it to exact authored hashtags. A page limit and statement
timeout do not bound the rows examined by a body scan, so the Worker must not
fall back to `ILIKE` or regex over `content.posts.body`.

The untagged discovery feed remains available and chronological. The mobile
search screen keeps the query in its route, supports cursor pagination and
refresh, and shows a retryable unavailable state. Guest callers use only the
public discovery route. The Worker validates a single 1–64 character hashtag
token and rate limits tagged requests before returning unavailable.

## Invoked-route inventory

| Destination | Current caller and route | Runtime result |
| --- | --- | --- |
| Discovery | Existing shell `/` → `HomeFeedNavigator`; untagged provider uses the native discovery feed | `GET /api/feed/discover`, public chronological keyset page |
| Tag search | Top bar → `router.go('/search')`; query is stored as `/search?q=...` | `FeedSearchNotifier` → `getDiscoverFeed(tag: ...)` → `GET /api/feed/discover?tag=...`; returns explicit `503 tag_search_unavailable` until the index gate below is met |
| Trending | Existing top bar → `router.go('/trending')` | `TrendingFeedScreen` → `TrendingFeedNotifier` → `getTrendingFeed`; remains `TRENDING_UNAVAILABLE`, with no native endpoint or approved ranking policy |
| Post detail | Search result → existing named `post` route (`/post/:postId`) | Existing post detail provider and API |
| Author profile | `FeedCard` and post detail author name → existing named `profile` route (`/user/:userId`) | Profile destination remains owned by the parallel profile task |

Search result navigation pushes the canonical post route, leaving `/search?q=...`
and its scroll position underneath. Search family identity includes the auth
token version; changing query or account disposes the old request and its Dio
cancel token. No router or profile-screen changes are part of this slice.

## Required before tagged search can be enabled

1. Approve a migration-backed exact-token index representation. The choice
   must account for body creation and edits, deletion, moderation/publication
   transitions, index backfill, and runtime read grants. No runtime body-scan
   fallback is permitted.
2. Add the migration and its backfill/maintenance behavior to the canonical
   PlanetScale migration path. This task does not create or apply production
   DDL.
3. Validate the query plan on the disposable PostgreSQL 17 scale test with
   both no-hit and common-tag distributions, cursor continuation, and filtered
   content. Use representative production corpus size once that size is
   approved for the test target. Record rows examined, buffers, and execution
   time; the planner must use the exact-token index and stay within an approved
   scan and latency budget.
4. Keep the existing visibility rules in the indexed query: active authors,
   public and published posts, allowed moderation, non-deleted rows, approved
   public authorship labels, and viewer block/mute isolation. Keep descending
   publication time plus post ID keyset ordering. A search must never return a
   partial scan as a successful empty or complete page.
5. After the migration and scale checks pass, review the exact migration head
   and explicitly activate the API path in a separate release.

The disposable scale probe in `apps/lythaus-public-api/tests/tag-search-scale.postgres.mjs`
measures the current unindexed candidate on 75,000 synthetic eligible rows. It
is intentionally isolated from the Worker runtime; production requests do not
execute that candidate query. Its assertion requires at least 99% of those
rows to be examined when no tag index exists, allowing for small integer
rounding differences in PostgreSQL `EXPLAIN ANALYZE` per-node row counters.

`apps/lythaus-public-api/tests/tag-search.postgres.mjs` also exercises the
native Worker against the disposable PostgreSQL database. It verifies the
tagged route fails closed, and separately verifies the existing untagged
discovery query excludes private/follower-only, pending, blocked, deleted,
inactive-author, blocked-author, and muted-author rows while its one-item
chronological cursor pages return each eligible fixture once. These checks
cover the active discovery path; the tagged query still requires equivalent
visibility and cursor coverage after an approved index-backed implementation
exists.

The local PostgreSQL 17.11 measurement on 2026-10-05 found no tag/body index.
For an absent tag, the planner used `posts_public_feed_idx`, examined 75,010
post rows, and reported 61.875 ms execution time with 1,970 shared buffer hits
and no reads. The row examination is the blocker; this warm-cache local timing
is not a production latency estimate or a safe scan bound.
