# Monthly rewards v0.5 preparation

This prospective candidate is separate from the recorded v1 and v2 policies.
It is inactive preparation: no deployment, migration execution, collection,
snapshot confirmation, redemption or feature activation is authorised by this
document. Existing signed catalogue bytes and historical calculators stay intact.

## Scoring and evidence

Both maintenance categories remain: MFA has a 250-point maximum and credential
maintenance has a 1,000-point maximum. A genuinely qualifying credential can
support both categories, for a combined maximum of 1,250. Each category requires
its own verified protection coverage and matching monthly authentication. Evidence
for one category does not establish the other category.

The new calculator unions overlapping protected intervals and known unprotected
intervals separately for each category. Known unprotected intervals share one
inclusive cumulative 24-hour allowance per calendar month. Unknown telemetry,
late enrollment and missing authentication remain insufficient evidence; they
are not treated as grace. Local lock preferences do not establish account
credential coverage or MFA.

Main currently produces canonical email-control and renewal observations.
The separately reviewed action-verification candidate produces existing-password
authentication evidence for the credential category only. Neither source provides
a server protection-coverage producer or an MFA producer. The v0.5 database adapter
therefore supplies no invented coverage, and those awards remain unavailable.
The optional suggestion producer is also not integrated by this preparation;
its absence is an explicit blocker. Independently qualified weekly credit is
retained when another component is unavailable. The contract can evaluate
server-supplied suggestion revisions using the existing quarterly evaluator.

Weekly ownership is approved: UTC Monday through Sunday, assigned to the month
containing the closing Sunday. The existing validator still checks complete weeks
and selects the best four. The v0.5 report records inherited policy, weekly rules
and contribution eligibility. Historical rules lacking the prospective human
contribution eligibility version remain visibly incomplete, without rewriting
their stored results.

All quarterly components retain calendar-quarter-end expiry, remaining source
months only and no earlier retroactive credit. The old 13,500 and 13,650 bounds
remain specific to their recorded versions. The present component arithmetic
still has a 13,650 candidate bound; `finalMaximumSourceMonth` is null for v0.5.
The final total requires recalculation when v0.5 is complete. Numeric validation
and component bounds remain enforced.

## Settlement and projections

The default settlement candidate remains 72 hours. It is provisional, configurable
and has not been justified by measured late-evidence data. The technical range
inherits the existing maintenance proposal's integer validation; it is not an
approved policy minimum, maximum or permission to shorten an existing period.
The database adapter requires an exact match with its immutable maintenance rules.
Changing recorded configuration in place is prohibited.

Jobs reconciles the closed prior month while current-month earning continues.
Known content, peer and contextual backlogs retain distinct pending reasons.
Policy/version/configuration failures are rejected, rather than converted to
zero points. Unresolved quarterly revision histories also block completeness.
Elapsed time alone never finalises a candidate. Missing coverage/suggestion
producers, settlement validation and snapshot/activation approvals remain blockers.

Explicit `MONTHLY_REWARDS_V05_RULES` configuration selects this preparation;
there is no configured default or provider change. The proposed SQL installs an
off feature flag, immutable rule sets and separate private candidate revisions.
It is not in the production migration manifest. Reconciliation uses a separate
check timestamp for bounded fair scheduling without changing report bytes.
Deletion erases private candidate records. Only the Jobs role can append them;
the Runtime role reads the authenticated member's current-period projection.

The existing private `/api/rewards/me/monthly` route exposes a sanitised optional
`prospective` sidecar, including candidate-only configurations. Confirmed fixed
snapshots and paid-tier selections retain their existing authority and coexist
with the sidecar. Flutter labels provisional benefits and displays a coexisting
confirmed level. The sidecar is always nonredeemable. Existing QR and invoice
claim paths still require a stored confirmed snapshot; there are no merchant
exceptions and no v0.5 snapshot promotion path.

## Remaining acceptance

Actual protection/MFA and suggestion producers, approved collection/privacy and
operational configuration, future source-month cutover, measured late-evidence
completeness validation, fixed snapshot finalisation and all existing activation
gates remain separate. Email/password, refresh tokens, optional device locks and
five-minute sensitive-operation verification remain owned by their existing lanes.
This preparation does not change credentials, sessions, providers or public posting.
