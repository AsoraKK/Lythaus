# Contribution feedback candidate

This is an inactive implementation candidate based on `23c607268b20102dc7014f0a0ceaf8511f9df7ed`. It does not authorize a production schema change, release, or feature activation. The Flutter candidate provider is hard-off, and the Worker route returns 404 unless its separate candidate flag is explicitly enabled. The existing legacy reaction endpoints and data remain unchanged; historical reactions are never mapped into either new channel.

## Contract

The candidate adds `GET /api/feedback/{post|comment}/{id}` and `PUT /api/feedback/{post|comment}/{id}/{quality|emotion}`. Reads return a typed target and independently counted `quality` and `emotion` objects, each with `counts` and the authenticated viewer's nullable `myValue`. Counts are recomputed from stored rows, exclude inactive actors and relationships blocked or muted by the viewer, and are returned with private, no-store caching. Guests may read public targets; a signed-in active account is required to change feedback.

The PUT body is `{ "value": ... }`; `null` removes the selection in that channel. Quality values are `like` and `dislike`. Emotion values are `amused`, `sad`, `angry`, `surprised`, and `appreciative`. Each actor can hold one choice in each channel for a given target. A required idempotency key identifies the same request across retries. The response acknowledges the requested change without replaying a potentially stale aggregate; the client fetches current counts after confirmation. The same session shares one controller between feed and detail. The account-bound recovery journal keeps an unconfirmed request and its original key, and a switch to another account clears the visible state. When the original account returns, the previous choice must be re-entered if the journal scrubbed its payload.

Visibility, declaration, moderation, deleted content, muted or blocked authors, blocked or muted comment ancestors, active accounts, self-interaction, and existing request/daily limits are checked. Changes and their zero-reputation activity record occur in one transaction. The actor row is locked so account deletion cannot finish its purge before an in-flight feedback write. No feedback event is emitted to the reputation or rewards pipeline.

`contribution-feedback-schema.sql` is a proposal outside the production migration directory. It defines typed post/comment foreign keys, one actor/target/channel choice, independent count indexes, proposed grants, and a privacy-locator extension. The Jobs candidate exports the subject's feedback and purges feedback authored by the subject or attached to their deleted content. Local tests apply the proposal only to a fresh disposable PostgreSQL 17 database after the verified baseline.

## Required before release

- Review and approve the schema, migration order, grants, rollback, data classification, retention, complete account export/deletion workflows, and production migration gate. Do not activate either candidate flag before coordinated API, Jobs, privacy, and schema acceptance. Run exact-head integrated CI and provider acceptance separately.
- Review concurrent block/follow/mute changes against the existing relationship mutation transaction model; the candidate uses the same visibility predicates but does not introduce shared relationship locks. Validate query plans and a batched read strategy: one summary request per visible item is unsuitable for a large feed or thread without rate and performance evidence.
- Review whether the current reporting of counts is appropriate for blocked/muted viewers. Independently test screen readers, physical devices, and privacy workflows end to end. The browser fixture uses synthetic local data and does not establish production behavior.
- No quality-vote-to-reputation formula has been approved here. Keep scoring unchanged until an explicit decision and separately tested anti-abuse policy exist.
- Formalize the candidate endpoints in the canonical OpenAPI bundle and generated clients after the contract and release sequence are reviewed.

The scoped Flutter suites cover the actual feed-to-detail journey, comment target, account-switch recovery, 200% text, media ordering, and existing feed, detail, comment and recovery behavior. Full Flutter analysis and native TypeScript checking pass.

Chromium runs the actual candidate feedback widget and feed card with an in-memory synthetic service at 390×844, 1440×960, and 320×960 with Flutter text scaling set to 200%. It exercises Like followed by Sad and checks that both selected counts remain visible. This is a component fixture, not an end-to-end production screenshot or a physical-device/screen-reader audit. Browser plugin was unavailable, so the repository's retained Playwright/Chromium setup was used. The local web build's existing secure-storage WebAssembly dry-run warnings remain; its JavaScript build succeeds.
